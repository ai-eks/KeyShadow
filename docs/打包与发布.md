# GitHub Actions 打包与发布

工作流为 `.github/workflows/package.yml`，名称 **Package Windows and macOS**。构建与测试命令见 [构建与测试](构建与测试.md)，本文说明分发流程。

## 触发与产物

| 触发 | macOS | Windows | GitHub Release |
| --- | --- | --- | --- |
| PR / push 到 main | 临时签名通用 DMG | 未签名 EXE | 不发布 |
| 手动运行，`sign_macos=false`（默认） | 临时签名通用 DMG | 未签名 EXE | 不发布 |
| 手动运行，`sign_macos=true` | Developer ID 签名、公证、附加票据的 DMG | 未签名 EXE | 不发布 |
| 推送 `v<VERSION>` tag | 必须完成签名、公证 | 未签名 EXE | 两平台全部成功后发布 |

DMG 内有通用 `键影.app`、`Applications` 快捷方式、平台说明、通用操作和双拼方案；Windows 提供无需附带 DLL 的单文件 EXE，本地构建目录附带同一套说明文档。

以 `VERSION=0.1.0` 为例，产物为：

```text
KeyShadow-0.1.0-macOS-universal.dmg
KeyShadow-0.1.0-Windows.exe
每个文件另附 <文件名>.sha256
```

Actions 页面运行详情底部的 `KeyShadow-macOS` / `KeyShadow-Windows` Artifacts 可下载，保留 30 天；任务 Summary 也提供链接。GitHub 会在外层再包一层 artifact ZIP，解压后即为 DMG 或 EXE 及校验文件。Release 附件则是直接可下载的版本文件。

## 版本

根目录 `VERSION` 是打包版本来源，使用三段数字 `X.Y.Z`，各段不超过 65534。macOS 构建时写入 app 的 `CFBundleShortVersionString`；Windows 在 `.build/` 生成临时 AssemblyInfo，将程序集和文件版本写为 `X.Y.Z.0`。构建不会修改两端源码中的版本声明。

发布前修改 `VERSION`，并在 `docs/changelog.json` 顶部添加同版本条目、提交并合并，随后从已验证提交创建对应 tag。工作流要求 tag 严格等于 `v<VERSION>`，如 `v0.1.0`；暂不支持带 `-rc` 等后缀。已有 Release 不会被重跑覆盖，应使用新版本发布。此配置本身不会替你创建或推送 tag。

## 更新日志

`docs/changelog.json` 按新到旧排列，每个版本需要日期以及中英文标题和要点：

```json
{
  "releases": [
    {
      "version": "0.2.0",
      "date": "2026-10-20",
      "zh": { "title": "一句话概括", "items": ["面向用户的变化"] },
      "en": { "title": "One-line summary", "items": ["User-facing change"] }
    }
  ]
}
```

每次运行工作流都会执行 `python3 tools/changelog.py check`：格式错误、顺序颠倒或缺少当前 `VERSION` 的条目都会让打包失败，修改版本号时请一并补上。发布时 `python3 tools/changelog.py notes <tag>` 生成双语 Release 正文，GitHub 自动生成的 PR 列表附在其后。[键影主页](https://keyshadow.aix.uy/) 会按最新 Release 的 tag 读取同一文件，发布后无需修改网站。

## 签名与公证配置

在仓库的 Settings → Secrets and variables → Actions 配置以下七项 Repository Secrets：

| Secret | 内容 |
| --- | --- |
| `DEVELOPER_ID_CERTIFICATE_BASE64` | 包含 Developer ID Application 证书及私钥的 `.p12` 文件，Base64 编码 |
| `DEVELOPER_ID_CERTIFICATE_PASSWORD` | 导出该 `.p12` 时设置的密码 |
| `DEVELOPER_ID_APP_IDENTITY` | 完整签名身份，如 `Developer ID Application: Name (TEAMID)` |
| `KEYCHAIN_PASSWORD` | CI 临时钥匙串使用的随机密码 |
| `APP_STORE_CONNECT_KEY_ID` | App Store Connect API key 的 Key ID |
| `APP_STORE_CONNECT_ISSUER_ID` | 该 API key 的 Issuer ID |
| `APP_STORE_CONNECT_API_KEY_BASE64` | 对应 `.p8` 私钥文件的 Base64 内容 |

这些是 GitHub 加密 Secrets，不是普通 Variables。GitHub 不提供回读已有 Secret 明文的接口，其他仓库里的设置也不会自动继承。请直接通过 GitHub 设置页或 `gh secret set` 交互录入；不要把证书、密码或私钥提交到代码库。

没有上述 Secrets 时，普通 PR、main 和默认手动打包照常工作；签名手动打包和 tag 发布会明确失败，不会降级为未公证 Release。工作流只在签名运行中导入临时钥匙串，步骤失败时也清理 `.p12`、`.p8` 和钥匙串。只有最终 Release job 具有 `contents: write` 权限。

公证分两步：先使用临时 ZIP 提交 app，确认 Apple 返回 `Accepted`，给 app 附加并验证票据，检查 Gatekeeper；然后生成最终 DMG，对 DMG 签名、公证并附加票据。这样 app 与 DMG 均携带离线验证所需的票据。临时 ZIP 不对外分发；最终只上传 DMG 和 SHA256。

实现参考：[GitHub 的 macOS 证书导入说明](https://docs.github.com/en/actions/how-tos/deploy/deploy-to-third-party-platforms/sign-xcode-applications)、[Apple 公证工作流](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow)。

## 本地打包与检查

```bash
# macOS：生成临时签名的通用 DMG
apps/macos/tools/package.sh

# 检查下载文件是否与校验文件一致（在解压后的包目录运行）
shasum -a 256 -c *.sha256
```

```powershell
# Windows PowerShell：生成单文件 EXE
.\apps\windows\tools\Package.ps1
```

本地已有 Developer ID 和 notarytool 凭证配置时，可给 `package.sh` 设置 `KEYSHADOW_SIGN_IDENTITY`、`KEYSHADOW_NOTARIZE=1`、`KEYSHADOW_NOTARY_PROFILE`；自定义钥匙串时另设 `KEYSHADOW_SIGNING_KEYCHAIN`。普通本地打包不需要证书。

macOS 脚本会挂载最终 DMG，验证 app 签名、双架构、包版本及 Applications 链接，再卸载镜像并核对校验和。Windows 脚本会检查最终 EXE 的实际文件版本并计算 SHA256。CI 运行纯数据测试，不请求桌面权限、不操作真实输入法。
